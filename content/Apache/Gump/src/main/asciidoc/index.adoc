== What is Apache Gump?

* The *first* continuous integration tool developed at the Apache Software Foundation
* Written in *Python*
* Builds software against the *latest development versions* of dependencies
* Detects *incompatible changes* within hours of a commit
* Sends *notifications* to project teams with detailed reports

[.notes]
--
Gump is unique because it doesn't just build a single project in isolation.
It builds many projects together, using the latest code from version control,
to detect cross-project incompatibilities as early as possible.
--

== The Problem Gump Solves

* Projects develop in isolation, unaware of downstream breakage
* A change in library A may break projects B, C, and D
* Without cross-project CI, breakage is discovered *too late* — at release time
* Manual integration testing doesn't scale across hundreds of projects

[.notes]
--
Before Gump, there was no systematic way to know that your commit to one
project would break another project that depends on you. Gump fills that
gap by building the entire dependency tree from source, every day.
--

== How Gump is Unique

* Builds projects against the *latest tip* of their dependencies
* Not just "does my project build?" — but "does the *ecosystem* build?"
* Tests cross-project compatibility *continuously*
* Covers Apache Ant, Apache Maven (1.x to 3.x), Gradle, and Makefiles

[.notes]
--
Most CI systems test a project against its declared dependency versions.
Gump instead uses the latest source of everything — including the latest
Ant, the latest JUnit, the latest XML parser — to find problems early.
--

== How Does Gump Work?

. Project definitions are mapped from *XML* into in-memory objects
. SCM update commands fetch the latest source for every module
. Builds are invoked in *dependency order*
. Build outputs feed into dependent projects
. Results are captured into *HTML reports*

[.notes]
--
Gump processes workspace XML descriptors that define modules, projects,
and their dependencies. It figures out the correct build order, updates
sources from version control, and builds each project in sequence.
--

== Build Tool Support

[cols="2*", options="header"]
|===
| Build Tool | How Gump Integrates

| Apache Ant
| Sets `build.sysclasspath=only`, manages system classpath

| Maven 1.x
| Runs with `--offline`, uses jar overrides

| Maven 2.x / 3.x
| Uses a *proxy server* for repository access

| Gradle
| Hooks into Maven's local repository and proxy

| Makefiles (e.g., httpd)
| Passes paths to freshly-built dependencies via command-line options
|===

[.notes]
--
Each build tool requires a different integration strategy. Gump's key
trick is ensuring that its freshly-built jars are used instead of
whatever the project might have checked into version control.
--

== Ant Integration Detail

* Gump sets the `build.sysclasspath` property to `only`
* This tells Ant: "ignore classpaths in build files; use the system classpath"
* Gump *manages* the system classpath to point to freshly-built jars
* Uses the latest Ant itself — built from tip of the master branch

[.notes]
--
To quote the Ant manual: "Only the system classpath is used and classpaths
specified in build files, etc are ignored. This situation could be considered
as the person running the build file knows more about the environment than
the person writing the build file."
--

== The Net Effect

[quote]
Every project is built every day with the latest version of every dependency — including the latest Ant, latest JUnit, latest XML parser.

* Results captured into *color-coded HTML pages*
* Extensive *hypertext links* for quick navigation
* Failures trigger *email notifications* to project teams

[.notes]
--
This is the core value proposition. It's like building the entire open source
stack from source, every single day, and telling you immediately when
something breaks.
--

== Project History

* *2000* — Created to solve integration pain building Apache Cocoon
* *2004* — Became an Apache Top-Level Project (February)
* Named after *Forrest Gump* — "GUBA" (Generate, Update, Build All) sounded like "Bubba Gump"
* First continuous integration tool at the ASF

[.notes]
--
The name has many fitting connections to the movie: the feather (adapted
for the original Gump icon mirrors the Apache feather), "Stupid is as
Stupid does" (captures many build errors), and "Life is like a box of
chocolates" — an apt description of building the latest versions of
everything together!
--

== Getting Started with Gump

=== What you need:

* *Python* runtime
* *Subversion* (for checking out Gump itself and workspace descriptors)
* A Unix-like environment (Linux recommended)
* Familiarity with XML for writing project descriptors

[.notes]
--
Gump is written in Python and uses XML workspace descriptors to
define what to build. The official instance uses Subversion for
both the Gump source and the workspace definitions.
--

== Source Repository

* Gump source is in the ASF *Subversion* repository:
** `https://svn.apache.org/repos/asf/gump/`
* Workspace descriptors define what gets built
* Project metadata lives in XML files

[source,bash]
----
svn checkout \
  https://svn.apache.org/repos/asf/gump/trunk \
  gump-trunk
----

[.notes]
--
The repository contains both the Gump engine (Python code) and the
workspace definitions (XML files describing projects and dependencies).
--

== Workspace Descriptors

* XML files that define *modules*, *projects*, and *dependencies*
* A module maps to a source repository checkout
* A project maps to a buildable unit within a module
* Dependencies link projects together

[source,xml]
----
<module name="ant">
  <svn repository="ant-svn"
       path="ant/core/trunk"/>
  <project name="ant">
    <ant basedir="src/main" target="dist"/>
  </project>
</module>
----

[.notes]
--
This is a simplified example. Real descriptors include dependency
declarations, output artifacts, and notification settings. The XML
format is specific to Gump — it is not a Maven POM or Ant build file.
--

== Defining Dependencies

[source,xml]
----
<project name="my-project">
  <ant basedir="." target="build"/>
  <depend project="ant" inherit="all"/>
  <depend project="junit"/>
  <depend project="commons-logging"/>
</project>
----

* `inherit="all"` — inherit the dependency's outputs onto the classpath
* Gump resolves the *full transitive graph* and builds in correct order

[.notes]
--
When you declare a dependency, Gump ensures that project is built first
and its outputs are available on the classpath. This is how cross-project
testing works — everything chains together.
--

. Point Gump at your workspace

== Reading the Results

* *Green* — project built successfully
* *Red* — build failed
* Detailed per-project pages show:
** Build command output
** Which dependencies were used
** What changed since last run
* Email notifications reference the online reports

[.notes]
--
The HTML reports are richly hyperlinked. From the main summary page
you can drill down into any failing project to see exactly what
happened and what changed.

== How to Contribute

* *Report issues* — file bugs or feature requests in JIRA
* *Improve documentation* — the website and workspace descriptors
* *Add project descriptors* — help Gump cover more of the open source ecosystem
* *Fix bugs* — the engine is Python, contributions welcome
* *Test and validate* — run Gump locally and report problems

[.notes]
--
One of the easiest ways to contribute is adding workspace descriptors
for projects that Gump doesn't currently build. This expands the
cross-project coverage without needing to modify the engine itself.
--

== Contributing a Project Descriptor

. Identify a project and its dependencies
. Write an XML workspace descriptor
. Test it with a local Gump run
. Submit a patch to the general@ mailing list
. Iterate based on feedback

[.notes]
--
Adding descriptor files is a great "good first contribution" because
it exercises your understanding of the project's build without requiring
Python coding skills.
--

== The Apache Way & Gump

* *Community over code* — the people matter more than the software
* *Open development* — discussion happens on public mailing lists
* *Earned authority* — commit access is earned through contributions
* *Lazy consensus* — silence is consent; object if you disagree

[.notes]
--
Like all ASF projects, Gump follows The Apache Way. The mailing list
is the canonical place where decisions are made. If it didn't happen
on the list, it didn't happen.
--

== Why Gump Still Matters

* Cross-project integration testing remains an *unsolved problem* at scale
* Most CI only tests within project boundaries
* Gump's philosophy: catch incompatibilities *before* release
* Valuable model for any ecosystem of interdependent libraries

[.notes]
--
Even with modern CI/CD, the problem Gump solves — testing across project
boundaries using the latest source — is still largely unique. If you
maintain a set of interdependent libraries, Gump's approach is worth
studying.
--
