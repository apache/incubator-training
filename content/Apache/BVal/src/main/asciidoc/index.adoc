== Apache BVal

image::project-logo.png[Apache BVal, 500]

Jakarta Bean Validation Implementation — TCK Compliant, Apache Licensed

[.notes]
--
Apache BVal delivers an implementation of the Jakarta Bean Validation 3.0 Specification which is TCK compliant, works on Java SE 11 or later, and uses the Apache Software License v2.0.
--

== What Is Bean Validation?

* A standard way to declare constraints on Java objects
* Annotations on fields, methods, and classes
* Validate data at any application layer
* Part of the Jakarta EE platform

[.notes]
--
Bean Validation provides a unified way to express constraints on your domain model using annotations. Instead of writing validation logic scattered throughout your code, you declare what valid data looks like right on the model class itself. It works in any Java SE or Jakarta EE environment.
--

== Why Do We Need It?

* Data validation is everywhere — forms, APIs, persistence
* Without a standard, validation logic gets duplicated
* Each layer re-implements the same checks
* Bean Validation: write once, validate anywhere

[.notes]
--
Before Bean Validation existed, developers would write validation logic in the UI layer, then again in the service layer, then again before persistence. Each copy could diverge. Bean Validation consolidates this into a single set of constraint declarations that can be enforced at any tier.
--

== What Is Apache BVal?

* Apache's implementation of Jakarta Bean Validation
* Current release: 3.0.2 (Jakarta Bean Validation 3.0)
* TCK (Technology Compatibility Kit) compliant
* Licensed under Apache License 2.0

[.notes]
--
Apache BVal is the ASF's implementation of the Jakarta Bean Validation specification. The current stable release is 3.0.2, released March 15, 2025, implementing Jakarta Bean Validation 3.0. It passes the official TCK tests, ensuring full specification compliance.
--

== Getting Started

image::project-logo.png[Apache BVal, 300]

Adding BVal to Your Project

[.notes]
--
Let's walk through how to add Apache BVal to a Maven project and start validating beans. The setup is straightforward since BVal artifacts are published to Maven Central under the org.apache.bval groupId.
--

== Maven Dependencies

[source,xml]
----
<dependency>
  <groupId>org.apache.bval</groupId>
  <artifactId>bval-jsr</artifactId>
  <version>3.0.2</version>
</dependency> <!-- also: bval-extras, bval-bundle -->
----
* **bval-jsr** — Core validation provider
* **bval-extras** — Additional constraints beyond the spec
* **bval-bundle** — OSGi bundle (includes bval-jsr)

[.notes]
--
Add bval-jsr to your pom.xml to get started. Maven will pull in the Jakarta Validation API and transitive dependencies automatically. The groupId is org.apache.bval for all modules. The bval-extras module provides additional constraints beyond the spec. The bval-bundle artifact packages everything with OSGi metadata for modular environments.
--

== Basic Usage: Create a Validator

[source,java]
----
ValidatorFactory validatorFactory = Validation
    .byProvider(ApacheValidationProvider.class)
    .configure()
    .buildValidatorFactory();

Validator validator =
    validatorFactory.getValidator();
----

[.notes]
--
This code explicitly requests the Apache BVal provider. You can also use Validation.buildDefaultValidatorFactory() which will discover BVal through the ServiceLoader mechanism if it's on the classpath. The explicit form shown here is useful when multiple providers are available.
--

== Basic Usage: Validate a Bean

[source,java]
----
Set<ConstraintViolation<MyBean>> violations =
    validator.validate(myBean);

for (ConstraintViolation<MyBean> v : violations) {
    System.out.println(
        v.getPropertyPath() + ": "
        + v.getMessage());
}
----

[.notes]
--
Call validator.validate() passing your annotated bean. It returns a Set of ConstraintViolation objects — one per failed constraint. Each violation tells you which property failed and the error message. An empty set means the bean is valid.
--

== Built-in Constraints (Jakarta Spec)

* `@NotNull`, `@NotBlank`, `@NotEmpty`, `@Size`
* `@Min`, `@Max`, `@DecimalMin`, `@DecimalMax`
* `@Pattern(regexp=)`, `@Email`
* `@Past`, `@Future`, `@PastOrPresent`, `@FutureOrPresent`
* `@Positive`, `@Negative`, `@Digits`, `@AssertTrue`

[.notes]
--
These are the standard constraints defined by the Jakarta Bean Validation specification. Any compliant implementation, including BVal, supports all of these out of the box. They cover nullability, size, numeric ranges, regex patterns, email format, temporal checks, sign constraints, and boolean assertions.
--

== Annotated Bean Example

[source,java]
----
public class User {
    @NotBlank private String name;
    @Email @NotNull private String email;
    @Min(18) @Max(150) private int age;
    @Past private LocalDate birthDate;
    @Size(max = 100) private String bio;
}
----

[.notes]
--
Here's a practical example. The User class declares that name must not be blank, email must be a valid email and not null, and age must be between 18 and 150. When you validate an instance of this class, BVal checks all these constraints and reports any violations.
--

== Custom Constraints

[source,java]
----
@Target({FIELD, METHOD})
@Retention(RUNTIME)
@Constraint(validatedBy = PhoneValidator.class)
public @interface ValidPhone {
    String message() default "Invalid phone";
    Class<?>[] groups() default {};
}
----

[.notes]
--
You can define your own constraint annotations. Create an annotation with @Constraint pointing to a validator class. The message, groups, and payload attributes are required by the spec. Your custom validator implements ConstraintValidator and provides the isValid() logic.
--

== Validation Groups

[source,java]
----
public interface OnCreate {}
public interface OnUpdate {}

public class Order {
    @Null(groups = OnCreate.class)
    @NotNull(groups = OnUpdate.class)
    private Long id;
}
----

* Apply different rules in different contexts
* Pass groups to `validator.validate(bean, OnCreate.class)`

[.notes]
--
Groups let you apply different validation rules depending on the context. For example, an ID should be null when creating a new entity but required when updating. You specify which groups to validate by passing them to the validate method.
--

== Integration with Jakarta EE

* Works with CDI — inject ValidatorFactory
* JAX-RS validates request/response automatically
* JPA can trigger validation on persist/update
* Works in any Jakarta EE compliant server

[.notes]
--
Bean Validation integrates deeply with the Jakarta EE platform. CDI containers can inject validators. JAX-RS will validate annotated parameters automatically. JPA fires validation events on lifecycle callbacks. BVal works anywhere a Jakarta Bean Validation provider is expected.
--
