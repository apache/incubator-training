== A Persistent Perl Interpreter

* Embeds a persistent Perl interpreter inside httpd
* Eliminates startup overhead of external CGI processes
* Gives Perl code direct access to the Apache C API
* Your existing CGI scripts still work — just faster

[.notes]
--
mod_perl gives you a persistent Perl interpreter embedded in your web server. This lets you avoid the overhead of starting an external interpreter and avoids the penalty of Perl start-up time, giving you super-fast dynamic content.
--

== More Than CGI on Steroids

* Manage Apache configuration from Perl
* Create custom authentication systems
* Build smart proxies and filters
* Implement stateful session management
* Customize every phase of the request lifecycle

[.notes]
--
As the project homepage says: "mod_perl is more than CGI scripting on steroids. It is a whole new way to create dynamic content by utilizing the full power of the Apache web server to create stateful sessions, customized user authentication systems, smart proxies and much more."
--

== How It Works

[source,text]
----
Client Request
     |
     v
Apache HTTP Server (httpd)
     |
     v
mod_perl (embedded Perl interpreter)
     |
     v
Your Perl Handler Module
     |
     v
Response
----

[.notes]
--
A request comes in to Apache. Instead of forking an external Perl process (as traditional CGI does), mod_perl has a persistent Perl interpreter already loaded inside the server process. Your handler code runs in-process, with full access to the Apache API.
--

== Two Generations

[cols="1,1"]
|===
| mod_perl 1.0 | mod_perl 2.0

| For Apache 1.3.x
| For Apache 2.0.x / 2.2.x / 2.4.x

| Version 1.31 (May 2009)
| Version 2.0.13 (October 2023)

| Stable, legacy
| Current recommended version
|===

[.notes]
--
mod_perl 1.0 targets the legacy Apache 1.3.x series. mod_perl 2.0 is the current active line, supporting the modern Apache 2.x series. The latest release is version 2.0.13, released in October 2023.
--

== Key Benefits

* *Performance* — no fork/exec overhead per request
* *Full API access* — hook into every Apache phase
* *Rich ecosystem* — hundreds of Apache::* / Apache2::* modules
* *Backward compatible* — CGI scripts run unmodified

[.notes]
--
The performance gain is the most immediate benefit, but the real power lies in accessing all phases of Apache's request processing: URI translation, authentication, authorization, content generation, logging, and more.
--

== Prerequisites

* Apache HTTP Server (2.0.x, 2.2.x, or 2.4.x) — built and installed
* Perl (5.x) — with development headers
* `apxs` — the Apache extension tool (usually in httpd's `bin/` directory)
* C compiler (gcc or equivalent)

[.notes]
--
Before installing mod_perl, you need the prerequisites: Apache httpd already installed with development headers, and a working Perl installation. The apxs tool is essential — it tells mod_perl how Apache was built.
--

== Building mod_perl

[source,bash]
----
tar -xvzf mod_perl-2.0.13.tar.gz
cd modperl-2.0
perl Makefile.PL MP_APXS=/path/to/bin/apxs
make && make test && make install
----

[.notes]
--
The build process is straightforward. The key parameter is MP_APXS, which should point to the apxs executable in your Apache installation. The test suite validates that everything works before installing.
--

== Enabling mod_perl in httpd

[source,apache]
----
# In httpd.conf:
LoadModule perl_module modules/mod_perl.so
----

* Restart Apache after enabling the module
* Check `error_log` for the mod_perl version string

[.notes]
--
Once installed, you enable mod_perl by adding the LoadModule directive to httpd.conf. On restart, the error log will confirm the loaded version, showing something like "mod_perl/2.0.13 Perl/v5.x.x configured".
--

== Your First Registry Script

[source,apache]
----
Alias /perl/ /home/httpd/perl/
<Location /perl/>
    SetHandler perl-script
    PerlResponseHandler ModPerl::Registry
    PerlOptions +ParseHeaders
    Options +ExecCGI
</Location>
----

[.notes]
--
ModPerl::Registry lets your existing CGI scripts run under mod_perl with minimal changes. The Alias maps a URL path to a filesystem directory, and the Location block tells Apache to handle requests there through mod_perl's Registry handler.
--

== A Simple Registry Script

[source,perl]
----
#!/usr/bin/perl
print "Content-type: text/plain\n\n";
print "mod_perl 2.0 rocks!\n";
----

* Save as `/home/httpd/perl/rock.pl`
* Make executable: `chmod a+rx rock.pl`
* Access: `http://localhost/perl/rock.pl`

[.notes]
--
This is the simplest possible registry script — it looks exactly like a CGI script. The difference is that under mod_perl, the Perl interpreter stays loaded between requests, eliminating startup time.
--

== Writing a Handler Module

[source,perl]
----
package MyApache2::Rocks;
use strict;
use warnings;

use Apache2::RequestRec ();
use Apache2::RequestIO ();
use Apache2::Const -compile => qw(OK);

sub handler {
    my $r = shift;
    $r->content_type('text/plain');
    print "mod_perl 2.0 rocks!\n";
    return Apache2::Const::OK;
}
1;
----

[.notes]
--
A handler module is the idiomatic mod_perl approach. The handler subroutine receives the request object ($r) which provides full access to the Apache API. This is where mod_perl really shines — you have access to every detail of the request and response.
--

== Configuring a Handler

[source,apache]
----
PerlRequire /home/httpd/perl/startup.pl

<Location /rocks>
    SetHandler perl-script
    PerlResponseHandler MyApache2::Rocks
</Location>
----

The startup file sets up `@INC`:

[source,perl]
----
use lib qw(/home/httpd/perl);
1;
----

[.notes]
--
PerlRequire loads a startup script at server start that sets up library paths. Then the Location block maps a URL to your handler module. Apache routes matching requests to your handler subroutine.
--

== Apache Request Phases

* URI Translation (`PerlTransHandler`)
* Authentication (`PerlAuthenHandler`)
* Authorization (`PerlAuthzHandler`)
* Content Generation (`PerlResponseHandler`)
* Logging (`PerlLogHandler`)

[.notes]
--
mod_perl lets you hook into every phase of Apache's request processing lifecycle. Most people start with PerlResponseHandler for content generation, but you can customize authentication, URL mapping, logging, and more — all in Perl.
--

== Migration: 1.0 to 2.0

* Enable the compatibility layer: `PerlModule Apache2::compat`
* Namespace changed: `Apache::` → `Apache2::`
* Constants moved: `use Apache2::Const`
* Full migration guide in the documentation

[.notes]
--
If you have existing mod_perl 1.0 code, the compatibility layer helps during transition. The main changes are namespace updates from Apache:: to Apache2:: and a new constants system. The project provides a comprehensive migration guide.
--
