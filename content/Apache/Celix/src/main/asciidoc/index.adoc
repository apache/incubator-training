== What is Apache Celix?

* A framework for *C and C++14* to develop dynamic modular software
* An implementation of the *OSGi specification* adapted for native code
* Uses *component and service-oriented programming* in-process
* Primarily developed in C with a C++ abstraction library

[.notes]
--
Celix brings the OSGi modularity model to the native/embedded world.
OSGi is well-established in Java for dynamic module systems; Celix
adapts those concepts—bundles, services, service registries—to C and C++.
--

== The Problem it Solves

* Native applications (C/C++) lack a standard *modularity framework*
* No dynamic service discovery or hot-swapping in traditional builds
* Monolithic designs make updates risky in *embedded* and *IoT* systems
* Need for runtime-installable components without full restart

[.notes]
--
In Java, OSGi solved the modularity problem decades ago. But for
embedded systems, IoT devices, and performance-critical native apps,
there was no equivalent. Celix fills that gap.
--

== Key Features

* *Runtime-installable bundles* — zip files containing shared libraries
* *Dynamic services* — register, discover, and track services at runtime
* *C and C++ support* — native C API plus C++ POCO abstraction layer
* *OSGi-inspired* — familiar model for anyone coming from Java OSGi
* *CMake integration* — purpose-built CMake functions for building bundles

[.notes]
--
Services in Celix are "plain old" structs with function pointers (C)
or "plain old C++ Objects" (POCO). The framework handles lifecycle
and dependency injection.
--

== Core Concepts

* *Bundle* — a zip file containing shared libraries and a manifest
* *Bundle Context* — the API a bundle uses to interact with the framework
* *Service* — a C struct or C++ object registered in the service registry
* *Service Registry* — central registry for publishing and discovering services
* *Container* — a running Celix framework instance with installed bundles

[.notes]
--
These concepts map directly to OSGi terminology. If you know OSGi,
you already understand Celix's architecture at a high level.
--

== How Services Work

[source,text]
----
┌──────────────────────────────────┐
│         Celix Framework          │
│  ┌────────────────────────────┐  │
│  │     Service Registry       │  │
│  └────────────────────────────┘  │
│     ▲ register    │ discover     │
│  ┌──┴───┐     ┌──▼───┐          │
│  │Bundle │     │Bundle │         │
│  │  A    │     │  B    │         │
│  └───────┘     └───────┘         │
└──────────────────────────────────┘
----

* Bundle A *registers* a service (struct with function pointers)
* Bundle B *discovers and uses* that service via the registry

[.notes]
--
Services are decoupled—Bundle B does not link directly against Bundle A.
The registry acts as the mediator, enabling dynamic composition.
--

== Use Cases

* *Embedded systems* — modular firmware with hot-swappable components
* *IoT gateways* — plugin-based protocol adapters
* *Industrial automation* — dynamic service composition
* *Networking equipment* — runtime-updatable modules

[.notes]
--
Anywhere you need modularity in native code without the overhead
of a full JVM. Celix is particularly well-suited to resource-
constrained environments that demand C/C++ performance.
--

== Prerequisites

* *Operating System*: Linux, macOS, or Windows (with Conan)
* *Compiler*: GCC or Clang with C11 and C++14 support
* *CMake* 3.18+
* *Conan* (optional, for dependency management)

[.notes]
--
Celix uses CMake as its build system. Conan can simplify fetching
dependencies but is not strictly required if you install them manually.
--

== Building from Source

[source,bash]
----
git clone https://github.com/apache/celix.git
cd celix
mkdir build && cd build
cmake -DCMAKE_BUILD_TYPE=Release ..
make -j$(nproc)
make install
----

[.notes]
--
The build produces the Celix framework libraries, built-in bundles,
and CMake config files for downstream projects to use via find_package.
--

== Hello World Bundle (C++)

[source,cpp]
----
#include <iostream>
#include "celix/BundleActivator.h"

class MyBundleActivator {
public:
  explicit MyBundleActivator(
    const std::shared_ptr<celix::BundleContext>& ctx) {
    std::cout << "Hello from bundle "
              << ctx->getBundleId() << std::endl;
  }
  ~MyBundleActivator() noexcept {
    std::cout << "Goodbye world" << std::endl;
  }
};

CELIX_GEN_CXX_BUNDLE_ACTIVATOR(MyBundleActivator)
----

[.notes]
--
The CELIX_GEN_CXX_BUNDLE_ACTIVATOR macro generates the entry points
that the framework calls when the bundle is started and stopped.
--

== CMake for Hello World

[source,cmake]
----
find_package(Celix REQUIRED)

add_celix_bundle(MyBundle
    SOURCES src/MyBundleActivator.cc
)

add_celix_container(MyContainer
    BUNDLES
        Celix::ShellCxx
        Celix::shell_tui
        MyBundle
)
----

[.notes]
--
add_celix_bundle creates the bundle zip. add_celix_container generates
a main executable that starts the framework with the listed bundles.
--

== Running the Container

[source,bash]
----
cd cmake-build-debug/deploy/MyContainer
./MyContainer

# Celix shell commands:
-> lb -a          # list all installed bundles
-> help           # list available shell commands
-> stop 3         # stop a bundle by ID
-> start 3        # start it again
-> stop 0         # stop the Celix framework
----

[.notes]
--
The built-in shell bundles (ShellCxx, shell_tui) provide a text
interface for inspecting and managing bundles at runtime. This is
extremely useful during development and debugging.
--

== Registering a Service

[source,cpp]
----
#include "ICalc.h"
#include "celix/BundleActivator.h"

class CalcProvider : public ICalc {
public:
  int add(int a, int b) override { return a + b; }
};

class CalcProviderActivator {
public:
  explicit CalcProviderActivator(
    const std::shared_ptr<celix::BundleContext>& ctx) {
    reg = ctx->registerService<ICalc>(
      std::make_shared<CalcProvider>()).build();
  }
private:
  std::shared_ptr<celix::ServiceRegistration> reg{};
};

CELIX_GEN_CXX_BUNDLE_ACTIVATOR(CalcProviderActivator)
----

[.notes]
--
Services are registered with a type (ICalc) and can include
properties (metadata). The registration is held via a shared_ptr;
when it goes out of scope, the service is unregistered.
--

== Using a Service

[source,cpp]
----
#include "ICalc.h"
#include "celix/BundleActivator.h"

class CalcUserActivator {
public:
  explicit CalcUserActivator(
    const std::shared_ptr<celix::BundleContext>& ctx) {
    ctx->useService<ICalc>()
      .addUseCallback([](ICalc& calc) {
        std::cout << "2+3=" << calc.add(2, 3)
                  << std::endl;
      })
      .setTimeout(std::chrono::seconds{1})
      .build();
  }
};

CELIX_GEN_CXX_BUNDLE_ACTIVATOR(CalcUserActivator)
----

[.notes]
--
useService provides ad-hoc access. For long-lived dependencies,
use trackServices to be notified when services appear or disappear.
--

== Tracking Services

[source,cpp]
----
class CalcTrackerActivator {
public:
  explicit CalcTrackerActivator(
    const std::shared_ptr<celix::BundleContext>& ctx) {
    tracker = ctx->trackServices<ICalc>().build();
    for (auto& calc : tracker->getServices()) {
      std::cout << "result: "
                << calc->add(2, 3) << std::endl;
    }
  }
private:
  std::shared_ptr<celix::ServiceTracker<ICalc>>
    tracker{};
};

CELIX_GEN_CXX_BUNDLE_ACTIVATOR(CalcTrackerActivator)
----

[.notes]
--
Service trackers provide continuous awareness of service availability.
They invoke callbacks as services come and go, making your code
reactive to the dynamic environment.
--
